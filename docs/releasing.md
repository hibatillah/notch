# CI and releases

Two GitHub Actions workflows in `.github/workflows/` do all of it. Nothing runs on pull requests, because the project
takes none.

| Workflow | Starts when | Does |
| --- | --- | --- |
| `ci.yml` | a push to `master` or `main` (a tag push does not start it) | `cargo fmt --all --check`, `cargo clippy --workspace -D warnings`, `cargo test --workspace`, `cargo build --release --workspace` |
| `release.yml` | a push of a tag that starts with `v` | the same checks, then builds and publishes a GitHub release |

Both install the MSVC toolchain, because the settings crate (GPUI) does not build with the GNU one. Locally use `cargo +stable-x86_64-pc-windows-msvc` for the settings crate.

`scripts/perf.sh` is not in CI: it moves the mouse and needs a real, unlocked desktop. Run it yourself before a release.

## Publish a release

1. Set `version` in `Cargo.toml` and `settings/Cargo.toml` (for example `0.2.0`; `store/Cargo.toml` too, to keep them equal) and commit it to the default branch.
2. Wait for the CI run on that commit to pass.
3. Tag the commit and push the tag:

   ```
   git tag v0.2.0
   git push origin v0.2.0
   ```

The release workflow stops at once if the tag does not match the version in `Cargo.toml` or in `settings/Cargo.toml`, so a tag can never publish a
build under the wrong number. It then produces a release named after the tag with:

- `<name>-v0.2.0-windows-x64-setup.exe`: the installer, built from `installer/notch.iss` with Inno Setup. It installs
  the notch and the settings program (`notch-settings.exe`, which the tray menu starts from the notch's folder) for the
  current user (no administrator rights), with the project license, the license of the font built into the notch
  (`Geist-LICENSE.txt`) and `THIRD-PARTY-LICENSES.txt` beside them, adds a Start menu entry and, unless unticked, starts the notch with Windows
- `<name>-v0.2.0-windows-x64-setup.exe.sha256`: its SHA-256 checksum
- release notes generated by GitHub from the commits since the previous tag

`<name>` is the package name in `Cargo.toml`, so renaming the crate renames the installer with no workflow change.

## Third-party licenses

`THIRD-PARTY-LICENSES.txt` holds the license texts copied from the sources of every crate linked into the two
executables (the settings program links Apache-2.0 GPUI crates, which require their license text to ship). It is
committed and generated: run `scripts/third_party_licenses.sh` after any `Cargo.lock` change and commit the result. The
script reads `cargo metadata` for the MSVC target, follows normal dependencies only, and groups crates by identical
text. Crates whose sources contain no license file are listed at the end of the file with their declared license.

## Updating

A user updates by downloading the newer `-setup.exe` and running it. The installer finds the copy that is already
installed (by its fixed `AppId` in `installer/notch.iss`), says which versions are involved and asks whether to
continue, then closes the running notch, replaces it in place and starts it again. Nothing in the notch checks for new
versions or uses the network for it. Never change the `AppId`, or the installer stops recognising earlier installs.

## Notes

- The orange folded-tab icon comes from `assets/branding/logo.png`. Regenerate `logo.ico` with
  `scripts/export-icon.sh` after changing it. Cargo embeds it in the executable; Inno Setup uses the same export for
  the setup executable and the master PNG for the wizard header. The Start menu shortcut and installed-app entry use
  the icon embedded in `notch.exe`.
- The installer is not code-signed, so Windows SmartScreen may warn people who download it. Free signing for open
  source projects exists (SignPath Foundation); it needs an application from the project owner, and signing is then one
  more step in `release.yml`.
- The installer is built only by the release workflow. To build it by hand, install Inno Setup and run
  `ISCC /DAppVersion=0.2.0 /DExeName=notch.exe /DSourceExe=<release notch.exe> /DSettingsExeName=notch-settings.exe /DSourceSettingsExe=<release notch-settings.exe> installer
otch.iss`; the result
  goes to `installer\Output` unless `/O` says otherwise (the workflow uses `dist`).
- Both workflows install the latest stable Rust (MSVC host), so a new Rust release can add a Clippy warning that fails CI. Fix the
  warning; do not pin an old compiler unless a release is urgent.
- To delete a bad release, delete the release and its tag on GitHub (or `git push --delete origin <tag>`), fix, and tag
  again.
